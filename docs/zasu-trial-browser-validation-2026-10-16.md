# ブラウザー認証導線の修正・検証（2026-10-16 JST）

## 原因と対応

既存のアカウントセッションはsessionStorageでタブ単位に管理されている。アプリが開いた新しいタブに既存タブのログイン状態がないこと自体は、この設計の結果である。
問題は、URL fragmentから取得したtrial_requestをメモリーにしか保持しないままURLから除去していた点。ログイン前やコード入力中にページを再読み込みすると承認先が失われた。また、承認欄は通常のダッシュボードの下にあり、表示されても気付きにくかった。

- 認証要求IDと上限10分の有効期限をタブ内に保持。JWT・コード・ライセンス本体は追加保存しない。
- 新規登録・ログイン・コード入力画面を経ても同一要求で承認へ戻る。ページ更新時は未入力のOTP欄と既存チャレンジ・再送待ち時間を復元し、自動再送しない。
- 新規登録で明示的に行った同意を、当該チャレンジの継続に限って保持。レビューで見つかった「更新後の再送がconsent_requiredになる」経路も修正。
- 承認欄をダッシュボード先頭に配置し、製品名へフォーカス・スクロール。承認は常に本人のボタン操作で実行する。
- 同一オリジンのログイン済みタブへ、ボタンから要求IDを受け渡せる。BroadcastChannelに送るのは要求ID・期限・タブ識別子・状態通知のみ。アカウントJWT・OTP・署名付きライセンスは共有しない。
- BroadcastChannelが使えない場合は、そのまま元の新規タブでログインできる。手動URLコピーは不要。
- 同一ドキュメント内の新しい要求fragmentもhashchangeで捕捉。明示的ログアウト時は要求を破棄し、別アカウントへの持越しを防ぐ。
- 一時的なinspect障害は同一要求の再取得ボタンで復旧。期限切れ・無効要求は破棄。再ログインやコード再送による通信障害の回避を要求しない。

タブ内の10分はクライアントの表示・継続上限であり、サーバー側の要求期限・認可を延長しない。製品の試用期間を変更する処理は追加していない。

## 再現と検証

修正前に、新規タブでのログイン/登録、要求ページ更新、OTP画面更新で失敗するテストを確保。追加レビューで見つかった新規登録OTP再送も、同意falseを拒否するモックを使い修正前失敗・修正後成功を確認した。

ローカルLinux/Chromium：認証・アカウント・ローカル検証サーバーの回帰41件成功。
ローカルLinuxのサイト全体549件も成功。OS別CIはコミットに紐付くGitHub Actionsを参照。件数だけで実機認証成功とは扱わない。

初回OS別CIでは、Macの追加再送テストに待機条件の欠陥（再送ボタンが無効＝完了と誤認）があり、Windowsでは既存アカウント用テストサーバーのroot+"/"判定が全ファイルを403にしていた。前者は150msの遅延応答を与えるとLinuxでも修正前失敗を再現し、保存チャレンジの再送時刻更新と送信ボタンの有効化を待つ修正で成功。待機時間延長・テストスキップは行わない。Windows側はpath.sepによる正しいディレクトリー境界へ修正。再送待ち時間の経過はテスト専用sessionStorageのダミーチャレンジを過去時刻にする隔離fixtureで検証する。ブラウザーの時計と実アカウントの期限は変更しない。

ブラウザーテストはHTTPをモックし、実アカウントのOTP送信・trial begin/approve/exchangeは行わない。既存ライセンス、既存期限、データベース、公開フラグは変更しない。
CIはLinux/macOS/Windowsでブラウザー認証回帰を実行し、Linuxでは静的ページ生成後にサイト全体のテストも実行する。デプロイ・署名鍵・Supabaseシークレットは使用しない。

## Mac実機の追加確認（09:25–09:31 JST）

サイトをe5ef3d4へff-only更新し、ローカル検証サーバーを再起動。ユーザーが既存タブにメールアドレスが表示されることを確認した。途中の「ログイン画面になる」という報告は本人が訂正したため、OTP送信・再ログインは実施していない。

認証済みアプリは不要なbeginを拒否するため、ブラウザー導線に限定した検証要求を作成した。Nodeからステージングのbeginへvocal/macと暗号学的乱数のchallengeを送り、Chromeの新しいタブを自動で開いた。verifierを保有せずexchangeは呼ばないため、この試験では署名付きライセンスを発行しない。署名鍵・既存キャッシュ・実grantの期限変更は不要。

ユーザーのテキスト報告で次を確認：

1. 新タブに「ログイン済みのタブで承認する」が表示。
2. ボタン操作後、既存タブにZASU VOCALの承認欄が表示。URLの手動コピーはなし。
3. 明示承認後、既存タブに「承認しました。製品に戻って認証の完了を確認してください。」が表示。
4. 新タブにも同じ完了通知が表示。

これはブラウザーの要求受け渡し・承認・通知の実機成功であり、この試験から新規ライセンス受信・ネイティブ認証を成功と推論しない。新規登録とOTPを伴う新タブ単独ログインの実機検証も別ゲート。今回の証拠はユーザーのテキスト報告とコード経路に基づく。
